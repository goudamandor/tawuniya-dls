Section 01

Purpose

Tawuniya's digital portals — including A'amal, the SME business-insurance portal — have historically been designed desktop-first. This guideline defines one shared, evidence-based responsive framework for Product Design, UX/UI Design, Development, Design System, Product Management, and QA.

The framework uses exactly three responsive categories — Desktop, Tablet, and Mobile — defined by available viewport width rather than device names. It replaces device-based thinking with space-based thinking: design for the width the page actually has available.

Design recommendation

Exact pixel breakpoints and other numeric values in this document are Tawuniya-specific recommendations, not universal industry standards.

NextPrinciples→
Section 02

Principles

  • Design for available space, not device names.
  • Use fluid layouts between breakpoints.
  • Introduce a breakpoint only when the layout genuinely needs to change.
  • Avoid designing for individual device models or resolutions.
  • Never allow important content, controls, or data to be clipped, hidden without access, or rendered unreachable.
  • Prefer reflow, re-stacking, and re-prioritization over shrinking.
  • Preserve information hierarchy at every width.
  • Preserve functionality across Desktop, Tablet, and Mobile.
  • Use horizontal scrolling deliberately and only where appropriate.
  • Treat foldables and dual-screen devices according to available viewport width, not as a fourth category.

Section 03

Global Research: How Major Systems Approach Responsive Design

The guideline synthesizes patterns from W3C/WCAG, Google Material Design, Microsoft Fluent/Windows, Apple's Human Interface Guidelines, IBM Carbon, Shopify Polaris, and Salesforce Lightning.

3.1 Responsive vs. adaptive design

Responsive design uses fluid grids, flexible images, and CSS media queries so one layout continuously adapts to viewport width. Adaptive design uses discrete layouts at defined breakpoints. Modern enterprise systems use a hybrid: fluid behavior within a size class, with structural changes at breakpoints.

Section 04

Challenging the 1080px Desktop Assumption

The initial brief proposed Desktop support down to approximately 1080px. The guideline evaluates that number against enterprise design-system patterns and realistic corporate laptop conditions.

  • 1366×768 remains a common laptop resolution, and a 1080px threshold can push real users out of Desktop mode before scaling or window resizing is considered.
  • At 125% Windows scaling, a 1366px-wide screen yields roughly 1093 effective CSS pixels before browser chrome and other deductions.
  • At 150% scaling, effective width can drop to roughly 910px on the same physical screen.
  • Enterprise users commonly resize browser windows for side-by-side work with Outlook, Teams, or Excel.
  • Browser chrome consumes horizontal space unevenly.
  • WCAG reflow means the Desktop lower bound is a UX/density decision, not an accessibility floor.
Tawuniya recommendation

Set the Desktop lower bound at 1024px, rather than 1080px or 1200px, and validate it against Tawuniya portal analytics when available.

Section 07

Foldable and Dual-Screen Devices

Foldables and dual-screen devices are an extension of ordinary responsive behavior, not a fourth breakpoint category.

7.1 Default rule

Classify a foldable by its current available viewport width using the same Mobile / Tablet / Desktop ranges.

7.2 When special handling is needed

Special handling is warranted when a hinge or fold genuinely splits the display into multiple logical segments. CSS Media Queries Level 5 provides viewport-segment features for this case.

  • Never place interactive controls, form fields, or critical text directly under a hinge/fold seam.
  • For two side-by-side segments, prefer a two-pane layout when appropriate.
  • For vertically stacked segments, place primary content in the top segment and secondary controls or a keyboard-adjacent panel in the bottom segment.
  • When one segment is reported, fall back entirely to ordinary width-based responsive rules.

8.5 Data tables

Tables must not simply shrink until they become unusable. Tablet can use column prioritization and confined horizontal scrolling; Mobile can transform rows into labeled cards or use horizontal scroll for genuinely tabular tasks. Every data point must remain reachable.

Section 09

Container Strategy

Tawuniya portals use a hybrid container strategy: constrained content by default, with full-width dashboards as a deliberate exception.

BehaviorWhen to use it
Stretch / full-bleedDashboards, data grids, and list views where extra width increases useful information density
Remain constrainedForms, detail pages, settings, policy documents, help/article content
ReflowMulti-column layouts crossing a breakpoint
StackSide-by-side layouts when the minimum comfortable column width can no longer be supported

Standard content uses a 1440px maximum width and is centered. Dashboards and dense list/grid views may use full-bleed containers while individual widgets retain sensible internal constraints.

Section 10

Grid System

The recommended Tawuniya grid is 12 columns on Desktop, 8 on Tablet, and 4 on Mobile.

10.1 Nested grids and card spans

Nested grids are supported. Card spans should be defined in column units rather than fixed pixels. Example: a card spanning 4 of 12 columns on Desktop can become 4 of 8 on Tablet and 4 of 4 on Mobile.

10.2 Practical example

A policy-summary dashboard can use three KPI cards at 4/12 each on Desktop, 4/8 on Tablet, and 4/4 on Mobile.

Section 11

Typography

A separate type scale at every breakpoint adds maintenance overhead without proportional usability gain. The core type scale and weights remain consistent, while line length, spacing, and truncation adapt.

  • Primary reading content should not fall below 14px; 16px is preferred.
  • Display/hero headings may reduce one or two steps on Mobile when needed for fit.
  • Secondary dense-table metadata may use smaller text, but not below 12px.
  • Target long-form line length is 50–75 characters at Desktop.
  • Ellipsis is appropriate only for secondary metadata and must provide a way to view the full value.

11.3 Arabic, RTL, and mixed content

  • Arabic strings commonly run 20–30% longer than English equivalents; allow for this in component sizing.
  • Grid, navigation, icon directionality, and form button placement mirror horizontally in RTL.
  • Numbers, dates, and currency follow Tawuniya's established localization rules.
  • Mixed Arabic/English content requires correct bidirectional text handling.

Section 13

Accessibility & Zoom

  • WCAG 2.1 SC 1.4.10 Reflow: screens should remain usable at an effective width of 320 CSS pixels, with limited exceptions for inherently two-dimensional content such as data grids and maps.
  • WCAG 2.1 SC 1.4.4: text must remain usable up to 200% resizing without loss of content or functionality.
  • WCAG 2.2 SC 2.5.8: pointer targets should be at least 24×24 CSS pixels or have equivalent spacing; Tawuniya should aim for 44×44px for primary actions where practical.
  • Test at 100%, 125%, and 150% Windows scaling on common corporate resolutions.
  • All interactive elements must remain keyboard reachable with visible focus states.
  • Horizontal scrolling should be limited to explicitly exempted content such as genuinely tabular data.

A layout that passes only at 100% zoom on one fixed resolution has not been fully validated against this guideline.

Section 14

Orientation

Portrait and landscape are not separate responsive categories. Orientation is simply one input that changes available viewport width; the resulting width determines the responsive category.

ScenarioLikely categoryReason
Tablet portraitTabletTypical portrait width ~768–834px
Tablet landscapeDesktop-likeMany tablet landscape widths are ≥1024px
Mobile phone landscapeMobile or TabletDepends on the actual resulting width

A screen must accommodate whichever category its current width lands in rather than assuming a device always presents one orientation.

Section 15

Responsive Rules

  • Design for available space, not device names or orientation labels.
  • Use fluid layouts between the three defined breakpoints.
  • Add a breakpoint-specific rule only when the layout genuinely breaks.
  • Validate Arabic/RTL alongside English/LTR at the same breakpoint.
  • Never allow important content to be clipped, permanently hidden, or unreachable.
  • Prefer reflow and transformation over shrinking text, controls, or touch targets below minimums.
  • Preserve information hierarchy and full functionality across all ranges.
  • Use horizontal scrolling only where the guideline explicitly permits it.
  • Treat foldables through viewport width and viewport-segment enhancement, never as a fourth category.
  • Validate layouts under 200%/400% zoom and common Windows scaling levels.
  • Define grid and card spans in column units, not fixed pixels.

  • 24px margins and 8-column grid with 16px gutters.
  • Collapsible drawer and condensed header.
  • 2-column cards where appropriate.
  • Prioritized/scrollable data tables with sticky header + first column.
  • Overflow menus for secondary/tertiary actions beyond roughly 4–5 actions.

Mobile 0–767px

  • 16px margins and 4-column grid with 12px gutters.
  • Full-screen overlay navigation and icon-focused header.
  • Single-column cards and dashboards.
  • Tables transform to card-per-row.
  • Full-width primary actions, full-screen modals/pickers, and bottom sheets for overflow actions.

Section 17

Design System Implementation

17.1 Figma

  • Create shared number variables: Breakpoint/Desktop = 1024, Breakpoint/Tablet = 768, Breakpoint/Mobile = 0.
  • Create saved grid styles: Desktop/12-col, Tablet/8-col, Mobile/4-col using the documented gutters and margins.
  • Use Auto Layout with Fill container / Hug contents instead of fixed widths wherever possible.
  • Expose Density or Breakpoint variants on complex components with Desktop / Tablet / Mobile states.
  • Use explicit responsive variants for transform-level changes such as tables → cards and drawer → overlay.
  • Set min/max widths for key components such as modals so Figma communicates implementation constraints.

17.2 Development

Desktop: min-width: 1024px
Tablet: min-width: 768px and max-width: 1023px
Mobile: max-width: 767px
  • Adopt a mobile-first cascade.
  • Express breakpoints as CSS custom properties using the same values as Figma.
  • Layer viewport-segment media queries on top of standard width-based rules as progressive enhancement.
  • Use logical CSS properties such as margin-inline-start and padding-inline-end for RTL-safe layouts.

Section 20

Tawuniya Responsive Design Standard — v1.0

Bookmark this section

This is the summary designers and developers should use as the day-to-day reference.

BreakpointRangeGridGutterMargin
Mobile0–767px4 columns12px16px
Tablet768–1023px8 columns16px24px
Desktop1024px+12 columns24px32px (48px on very wide monitors)

Most important rules

  • Exactly three responsive categories: Desktop, Tablet, Mobile — defined by viewport width.
  • Desktop starts at 1024px, not 1080px.
  • No fourth Foldable category; foldables follow width-based rules with viewport-segment enhancement where needed.
  • Data tables never simply shrink; use column hiding/scroll on Tablet or card transformation on Mobile, keeping every data point reachable.
  • WCAG 1.4.10 Reflow and 2.5.8 Target Size are minimums at every breakpoint.
  • Arabic/RTL is validated alongside English/LTR at every breakpoint.
  • Grid spans use 12/8/4 column units.
  • Use constrained 1440px content for reading/forms and full-bleed behavior for dashboards.
